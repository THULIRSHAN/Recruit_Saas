| **Q19** | Found starting M7 (Candidate Profile & Applications): Q11 decided CANDIDATE is implicit (no `UserOrganizationRole` row) and that candidate-owned actions are "authorized via ownership checks... not a role lookup" — but `authorization.md` §3 explicitly seeds `candidateProfile:update`/`application:create`/etc. as CANDIDATE permissions, and `CLAUDE.md` rule 1 requires *every* protected endpoint to use `@RequirePermission()`. `PermissionsGuard` as built only ever read the `roles`/`isSuperAdmin` claims from the access token, neither of which can ever contain `'CANDIDATE'` for anyone (per Q11) — so no candidate-facing endpoint could ever pass `@RequirePermission()`, for *any* user, as the guard was originally written. | `authorization.md` §3, `CLAUDE.md` rule 1, Q11, Q3/REQ-AUTH-008, M7 (Candidates) | **Decided:** `PermissionsGuard` now always includes `'CANDIDATE'` in the role keys it checks, for every authenticated user, unconditionally (not just as a fallback when they hold no org roles) — per Q3/REQ-AUTH-008, the same login can be both org staff and a candidate, so a Recruiter should also pass `application:create`. This lets candidate-facing endpoints use the same centralized `@RequirePermission()` mechanism as everything else, satisfying `CLAUDE.md` rule 1 without contradicting Q11's data-model decision (still no `UserOrganizationRole` row for candidates) — the *resource-level* restriction (only your own profile/application) remains a required second layer via an ownership check in the service, the same pattern `authorization.md` §3 already prescribes for Interviewer's ownership-scoped permissions. |

Swapping in a real `CloudinaryStorageService` later only requires a new class + one line in `StorageModule`'s provider registration; `StorageController` itself is local-storage-specific and would become dead code at that point (a real Cloudinary URL needs no local proxy). |

## Risks (separate from the above — things to watch, not decisions to make now)

- **Bottleneck risk:** Phases 3-4 (database + auth/RBAC) block nearly everything else. If those slip, the whole team stalls. Mitigation: assign the strongest available developers there and treat it as the first priority, per `team-plan.md` §1.
- **Tenant-isolation regression risk:** with 5 developers of varying experience touching tenant-owned data, a single missed `organizationId` filter is a critical security bug that's easy to introduce and easy to miss in casual review. Mitigation: the `TenantScopedService` base pattern (`multi-tenancy.md` §4) plus the mandatory cross-tenant test case (`testing.md` §2 case 5) as a hard PR gate.
- **Scope risk:** the full feature list (25 functional areas) is large for a semester team of 5. Mitigation: the MVP scope cut in `team-plan.md` §7 exists specifically to protect a working end-to-end demo over broad-but-shallow coverage.
- **Knowledge-silo risk:** module ownership (`team-plan.md` §3) reduces conflicts but risks each developer only understanding their own slice. Mitigation: code review across owners (not just within a module), and this documentation set existing so anyone can ramp on any module.
- **"It works on my machine" risk:** without the Docker/CI setup in Phase 2 being solid early, integration surprises pile up late. Mitigation: prioritize Phase 2 completeness (docker-compose, CI skeleton) before feature work fans out.
