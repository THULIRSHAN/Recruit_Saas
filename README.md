# Applicant Tracking & Recruitment Management SaaS — Project Documentation

This is the **Phase 1 deliverable**: complete requirement engineering and architecture analysis, produced before any application code. Per the team's working agreement, implementation does not begin until the team has reviewed this and confirmed the open decisions below.

## Start Here

1. **`docs/open-questions.md`** — read this first. Ten specific decisions need team confirmation before certain phases can start; each has a recommendation, none are final.
2. **`docs/requirements.md`** — system overview, actors, functional & non-functional requirements, detailed specs for every MVP-critical (P0) requirement.
3. **`docs/architecture.md`** — module breakdown, why a modular monolith, component diagram, user journeys (User → Page → Action → API → DB → Result) for every major workflow.
4. **`docs/database.md`** — entity list, ERD description, full Prisma schema proposal, index strategy.
5. **`docs/authentication.md`** / **`docs/authorization.md`** / **`docs/multi-tenancy.md`** — the three documents that together define the security model; multi-tenancy in particular should be read by every developer before touching any endpoint.
6. **`docs/api.md`** — REST conventions + frontend (Next.js) architecture.
7. **`docs/security.md`** / **`docs/testing.md`** — security checklist and required test coverage per endpoint.
8. **`docs/deployment.md`** — Docker/Nginx/CI-CD design.
9. **`docs/team-plan.md`** — phased implementation order, dependency map, per-developer module ownership for the 5-person team, git workflow, recommended MVP scope.
10. **`docs/decisions/`** — ADRs recording the "why" behind the five biggest architectural calls (modular monolith, tenancy strategy, RBAC model, file storage, AI-deferred).
11. **`CLAUDE.md`** — the condensed operating rules for whoever (human or AI) writes code in this repo from here on.

### Frontend build (F-series)

Modeled on a user-supplied Hirelane HTML/CSS/JS clickable prototype (19 screens across the public marketplace, candidate portal, org/recruiter portal, and admin portal), built against the completed backend above.

F1-F6 complete as of 2026-09-05 -- every one of the prototype's 19 screens is built and wired to the real backend, closing out the frontend build alongside the P0-P2 backend above:

- **F1 (Foundation)**: Tailwind v4 design tokens ported from the prototype, a shared UI component kit, a fetch-based API client with silent access-token refresh (deduplicated against React Strict Mode's double-effect-invoke), `AuthProvider`/`useAuth`, backend CORS enabled (`FRONTEND_URL`).
- **F2 (Public marketplace)**: job search + job detail, server-rendered against `GET /jobs/search` / `GET /jobs/public/:id`.
- **F3 (Auth)**: login, candidate signup, org signup, wired to `/auth/*` and `POST /organizations`.
- **F4 (Candidate portal)**: dashboard, application list/detail/withdraw, offer review, job application form, full profile management (about/CVs/experience/education/skills).
- **F5 (Org/recruiter portal)**: dashboard, job create/edit + pipeline-stage management, a per-job kanban board, application detail (stepper, evaluations, screen/decide actions), interview scheduling, offer creation, and the interviewer's own evaluation-submission screen. Added `GET /organizations/me/members` (no endpoint previously existed to pick an interview panel).
- **F6 (Admin portal)**: platform overview (`GET /admin/analytics`) and the organization approval queue (Pending/Active/Rejected, approve/reject with reason).

Two real bugs found via manual testing and fixed: a token-refresh race condition (Strict Mode double-invoke racing a single-use refresh token) that could wrongly log out a valid session, and a candidate-profile crash from assuming `PATCH /candidates/me/education|experience|skills` return the full profile when they return just the replaced list. The entire org+candidate hiring flow (post job → publish → apply → screen → schedule interview → evaluate → hire → offer → accept) was verified end-to-end against the live backend. Deliberately not built: an audit-log table (no read endpoint exists yet, write-only) and a platform-growth chart (no schema field marks status-transition timestamps, Q32) -- both would have required fabricating data (see `docs/open-questions.md` Q33).

**F7 (2026-09-05)**: UI for the five backend modules the prototype had no screens for -- Notifications (a shared list component reused across all three portals), Subscriptions (plan selection + payment history, Company Owner), Talent Pools (create/tag/untag, Recruiter -- tagging happens from an application's detail page since there's no separate candidate directory, per Q30), University Partnerships (org-side manage, admin-side catalog), and Onboarding (checklist creation/task management once an offer is ACCEPTED, on both the org's and candidate's offer pages). Every new endpoint verified against the live backend, including the full onboarding round trip (checklist → document upload → task completion).

**Post-F7 gap sweep (2026-09-05)**: reviewing what F1-F7 still left uncovered turned up two functional dead-ends and one missing standard flow, all fixed: pipeline templates had no management UI at all (F5's "Load Template" dropdown was silently empty for every org -- nothing could ever create one), staff invitations had no UI either (an org could only ever have the one user who registered it), and forgot/reset-password had no pages despite existing on the backend since M3. Added `/org/pipeline-templates`, `/org/team` + a public `/accept-invitation/[token]`, and `/forgot-password` + `/reset-password/[token]`. All three verified end-to-end via curl (create a template, invite + accept a teammate, reset a password and confirm the old one stops working). Also surfaced a real pre-existing doc/code mismatch, not something to fix as frontend work: Q2 says verification is required before offer acceptance, but `OffersService.respond()` never actually checks it -- flagged in `docs/open-questions.md` Q2 for a backend decision.

**Design-canvas reconciliation (2026-09-05)**: the user shared a Claude "design canvas" artifact -- a 30-screen design spec for this app, more detailed than the original clickable prototype. A background comparison against every built page found the color palette matched exactly everywhere already, but confirmed real gaps: icons were missing almost everywhere outside the two public pages fixed earlier (every sidebar nav item was a bare text label), there was no confirmation step before any destructive action (reject/withdraw/logout fired immediately), org settings had no "edit org name" UI despite the endpoint existing since M5, and there was no custom 404 page. Fixed all four: a shared icon set wired into every `AppShell` nav item and `EmptyState`, a shared `ConfirmDialog` wired in front of reject/withdraw/logout, a consolidated tabbed `/org/settings` (General/Team/Billing, folding two sidebar items into one and adding the missing name-edit form), and `app/not-found.tsx`. Deliberately deferred rather than silently skipped: an EmailVerification page and an org-wide "all offers" list the spec expects but nothing builds yet (the latter may need a new backend aggregate endpoint), a real 403/access-denied page, and skeleton loading states.

Also verified via a full `docker compose up -d --build`: fixed a container-networking gap (server components inside the frontend container couldn't reach the backend via `localhost`; added a server-only `INTERNAL_API_URL`) and wired `SUPER_ADMIN_EMAIL`/`SUPER_ADMIN_PASSWORD` into the backend container (previously only worked for native runs).

**Two real bugs found via user report and manual comparison against the original prototype screenshot (2026-09-05)**: the candidate profile's Experience editor had no date input fields at all -- it silently sent empty strings for `startDate`/`endDate`, which the backend correctly rejected (`must be a valid ISO 8601 date string`) since `@IsOptional()` only skips validation for `null`/`undefined`, not `''`. Fixed by adding real date inputs and sanitizing the payload. Separately, a plain unlayered `a { color: var(--accent) }` rule in `globals.css` was beating Tailwind's layered `.text-white` utility (CSS `@layer` semantics: unlayered always wins over layered, regardless of specificity), making the active "All roles" filter pill's text invisible; fixed by wrapping custom base styles in `@layer base`. Also added the search/location/save icons the public marketplace pages were missing.

**Deep-audit round 2 (2026-09-05)**: a further pass over the 12 mockup screens only shallow-checked (colors + icon count) in the design-canvas reconciliation above turned up smaller fit-and-finish gaps: dashboard/admin/org overview `StatCard`s had no icons wired despite the component supporting them, interviewer evaluation scores were shown as raw "n/5" text instead of the existing `Stars` component, the application detail page's side panel had no link back to the job posting, and CV row actions were text links instead of icon buttons with no working download (added `downloadCv()` against the existing signed-URL endpoint). All fixed in one pass across the three portal dashboards and the two detail pages.

**Org-wide Offers list + a real authorization bug it caught (2026-09-05)**: the design-canvas spec's `OfferTrackingList` screen had no backend endpoint to support it -- added `GET /organizations/me/offers` (HR Manager/Company Owner, paginated, status filter) and the `/org/offers` page consuming it. Its own cross-role e2e test caught a genuine bug: `offer:read` is granted to both `CANDIDATE` (self-scoped) and `HR_MANAGER` (org-scoped), and `PermissionsGuard` implicitly grants `CANDIDATE` on any route without `@RequireTenant()` -- this aggregate list has no `:id` param for `@RequireTenant()`/`TenantGuard` to use, so any authenticated org staff member (e.g. a Recruiter with no `offer:read` grant) could satisfy the check via the implicit fallback. Fixed with a new `@OrgScoped()` decorator, a purpose-built sibling to `@RequireTenant()` for id-less org-scoped routes, rather than changing `@RequireTenant()`'s existing contract. Also fixed the backend's dev-mode "email not sent, logged instead" links (verification, password reset, staff invitation), which pointed at raw backend API paths instead of the frontend pages that actually handle them -- two of the three were even POST-only endpoints, never clickable as logged. Added the missing `/verify-email/[token]` frontend page. Full backend suite (256 unit + 289 e2e) re-verified after the `PermissionsGuard` change; the new feature verified end-to-end against a rebuilt Docker stack via an isolated test org/job/candidate/offer created through the API, then checked in the browser.

**Staff removal + pending invitations (Q34, 2026-09-05)**: `requirements.md`'s role table has said Company Owner "invites/removes staff" since Phase 1, and `user:remove`/`role:assign` have sat seeded-but-unused in the permission catalog since M4 -- only the invite half was ever built, and the design-canvas `StaffInvite` mockup's unified members+invitations table with per-row actions had nothing behind it. Added `GET`/`DELETE /organizations/me/invitations[/:id]` (list/cancel pending invitations) and `DELETE /organizations/me/members/:userId` (revokes that user's org access only, leaving their account and any other org membership untouched); invented two safety rules neither doc specifies (can't remove yourself, can't remove the org's last Company Owner), documented in `open-questions.md` Q34 rather than guessed silently. `/org/team` now shows one list of active members and pending invitations with Remove/Cancel behind a `ConfirmDialog`, gated to Company Owner client-side. 14 new e2e tests; full suite (256 unit + 303 e2e) re-verified, and the whole flow (invite → list → cancel → invite → accept → remove → self-removal blocked) re-verified against the rebuilt Docker stack via the API.

**Platform admin audit log (Q33, 2026-09-05)**: `AuditLog` had been write-only since M5 -- Q33 flagged this rather than fabricating data for the admin portal's frontend when it was originally built. Added `GET /admin/audit-log` (Super Admin, paginated) and an `/admin/audit-log` page (actor, action, target, timestamp, prev/next). `auditLog:read` needed no new permission -- turned out to already be seeded onto `SUPER_ADMIN` since M4, the same "seeded but dead" situation `user:remove`/`role:assign` were in before Q34 (corrected Q33's own prediction that a new key would be needed). 4 new e2e tests; full suite (256 unit + 308 e2e) re-verified. Q33's other two items (a platform growth chart, a `GET /admin/users` list) remain out of scope for the reasons already recorded there.

## Running Locally

Requires Node.js 24 (see `.nvmrc`) and Docker Desktop.

```
cp .env.example .env
docker compose up --build
```

- Backend: http://localhost:3001 (health check at `/health`)
- Frontend: http://localhost:3000
- Postgres: `localhost:5432` (credentials in `.env`)

To run a single service outside Docker (faster iteration), install
dependencies once at the repo root (`npm install`) and use that workspace's
scripts, e.g. `cd backend && npm run start:dev` or `cd frontend && npm run
dev`. The Postgres container's port is published to the host, so a
natively-run backend can still reach it via the `DATABASE_URL` in `.env`.

### Common commands (run from repo root)

```
npm run lint         # both workspaces
npm run typecheck    # both workspaces
npm run test          # both workspaces
npm run build          # both workspaces
npm run format:check    # Prettier check, whole repo (code only, not /docs)
npm run format           # Prettier write, whole repo (code only, not /docs)
docker compose down -v # stop and wipe the local database volume
```
