| **Q11** | `authorization.md` §2 states "every role except SUPER_ADMIN is organization-scoped" (assigned via `UserOrganizationRole`), but a Candidate applies across any number of organizations without being a member of any of them — the schema has no way to give a Candidate an org-scoped role, and none of the candidate-owned tables (`CandidateProfile`, `Application`, etc.) are org-scoped. | **Q13** | No document specifies how the *first* Super Admin account is created — every registration flow (candidate, org owner) creates a `User` with `isSuperAdmin=false`, and there is deliberately no API to set it (exposing that would be a privilege-escalation hole). | **Q15** | Two gaps for `GET`/`PATCH /api/v1/organizations/me`: (1) `organization:read` isn't seeded on any org-scoped role (same gap as Q14, at the org-scoped level this time), so it's unclear who besides `COMPANY_OWNER` (holder of `organization:update`) can view org settings; (2) REQ-AUTH-002 states a `PENDING_APPROVAL` org "cannot post jobs, cannot log in to org portal beyond a pending approval screen" — implying writes should be blocked pre-approval, but doesn't say so for reads or explicitly for the settings-update case. | `authorization.md` §3, REQ-AUTH-002, M5.3 (Organizations) | **Decided:** (1) No permission gate on `GET .../me` at all — any authenticated user with an org in their token context (any org-scoped role) can view their own org's name/status/rejection reason, since every staff member needs to see the "pending approval" screen, not just the Owner. (2) `PATCH .../me` (still gated by `organization:update`, i.e. Company Owner only) additionally requires `status === ACTIVE`, returning 409 otherwise — consistent with "not usable... until approved." Revisit if a future role needs write access while pending. |
| **Q16** | `database.md`'s `Invitation` model stores a raw `token` (unique, plaintext) rather than a hash, unlike every other single-use token in the schema (`RefreshToken.tokenHash`, `VerificationToken.tokenHash`) — `authentication.md` §2 documents hashing bearer tokens at rest as the established pattern precisely so a DB read/leak can't be used to redeem them directly. Documentation/schema inconsistency, flagged per `CLAUDE.md`'s doc-conflict rule. | `database.md` (`Invitation`), `authentication.md` §2, M5.4 (Organizations) | **Decided:** Follow the established hashed-token convention, not the literal schema proposal — renamed the column to `tokenHash` in a new migration. Also: REQ-AUTH-008 says an invite carries "role(s)" (plural) but `Invitation.roleId` is singular with no join table for multiple roles. Decided to keep it singular for MVP scope (no `InvitationRole` join table) — inviting someone into two roles at once is done as two separate invitations to the same email; revisit only if the frontend UX genuinely needs a single combined invite. |

## Risks (separate from the above — things to watch, not decisions to make now)

- **Bottleneck risk:** Phases 3-4 (database + auth/RBAC) block nearly everything else. If those slip, the whole team stalls. Mitigation: assign the strongest available developers there and treat it as the first priority, per `team-plan.md` §1.
- **Tenant-isolation regression risk:** with 5 developers of varying experience touching tenant-owned data, a single missed `organizationId` filter is a critical security bug that's easy to introduce and easy to miss in casual review. Mitigation: the `TenantScopedService` base pattern (`multi-tenancy.md` §4) plus the mandatory cross-tenant test case (`testing.md` §2 case 5) as a hard PR gate.
- **Scope risk:** the full feature list (25 functional areas) is large for a semester team of 5. Mitigation: the MVP scope cut in `team-plan.md` §7 exists specifically to protect a working end-to-end demo over broad-but-shallow coverage.
- **Knowledge-silo risk:** module ownership (`team-plan.md` §3) reduces conflicts but risks each developer only understanding their own slice. Mitigation: code review across owners (not just within a module), and this documentation set existing so anyone can ramp on any module.
- **"It works on my machine" risk:** without the Docker/CI setup in Phase 2 being solid early, integration surprises pile up late. Mitigation: prioritize Phase 2 completeness (docker-compose, CI skeleton) before feature work fans out.
